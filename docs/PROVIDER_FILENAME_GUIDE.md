# 공급자 파일명 처리 지침

## 왜 이 규칙이 필요한가

다운로드 페이지에 표시되는 이름은 실제 저장 파일명과 다를 수 있다. 공급자가 개인정보 보호, 금칙어, 문자 호환성 또는 UI 정책 때문에 이름을 치환할 수 있기 때문이다. GigaFile에서는 다음 안내문이 실제 파일명 자리에 표시되는 사례가 확인됐다.

```text
●ファイル名が置換されました※DLしたファイルは、原題まま表示されます。●
```

이 현상은 ZIP 같은 압축파일에 한정되지 않는다. MP4, MKV, 문서 등 모든 일반 파일에도 발생할 수 있으므로 압축 해제 코드가 아닌 공통 다운로드 계층에서 처리해야 한다.

## 파일명 결정 우선순위

NASDrop은 아래 순서를 지켜야 한다.

1. 최종 다운로드 응답의 RFC 5987 `Content-Disposition: filename*`
2. 최종 다운로드 응답의 `Content-Disposition: filename`
3. 공급자 API 또는 공유 페이지에서 검사한 이름

리디렉션 응답이 여러 개면 마지막으로 유효한 `Content-Disposition`을 사용한다. `filename`과 `filename*`가 함께 있으면 UTF-8 원본을 담는 `filename*`가 우선이다.

실제 파일명은 다음 처리 전에 확정해야 한다.

- 작업 목록에 표시할 이름 갱신
- 압축파일 형식 판정
- 압축 해제 폴더명 결정
- 최종 목적지로 이동
- 같은 이름 충돌 처리

공급자가 본문 없는 HEAD 요청을 지원하면 링크 검사 단계에서 실제 파일명을 먼저 확인해야 한다. 그래야 작업이 큐에 등록되는 순간부터 정확한 이름을 표시할 수 있다. 실제 전송 중 헤더 수집은 HEAD 실패 또는 공급자 변경에 대비한 보조 경로로 유지한다.

## 안전 규칙

- `/`, `\\`, 제어문자, `.`·`..`, 경로 이탈 형태를 제거하거나 거부한다.
- 파일명 길이를 제한하고 기존 결과와 충돌하면 안전한 고유 이름을 만든다.
- 파일명 확인을 위해 본문을 두 번 다운로드하지 않는다. HEAD가 지원되면 HEAD를 사용하고, 아니면 실제 전송에서 받은 헤더를 사용한다.
- 응답 헤더는 `.nasdrop-tmp/<job-id>` 안에만 잠시 저장하고 처리 직후 삭제한다.
- 쿠키, 접근 토큰, Authorization 헤더는 작업 JSON, 로그, API 응답 또는 Git에 저장하지 않는다.
- 실제 이름을 얻지 못해도 다운로드 자체를 실패시키지 않고 검사 단계의 안전한 이름으로 대체한다.

## 필수 회귀 테스트

공급자 파서나 다운로드 파이프라인을 변경할 때 다음을 모두 확인한다.

- 위 GigaFile 일본어 치환 안내문 + 실제 UTF-8 한국어 MP4 이름
- 동일 상황의 ZIP·7z·RAR 등 압축파일
- `filename`과 `filename*`가 동시에 존재하는 응답
- 리디렉션으로 헤더 블록이 여러 개인 응답
- `Content-Disposition`이 없는 응답
- 경로 구분자와 `..`가 포함된 악성 파일명
- 동일한 실제 이름이 이미 목적지에 있는 경우
- 압축 여부와 관계없이 실제 이름이 작업 목록과 최종 결과에 동일하게 반영되는지

릴리스 전에는 `tests/test_processing_pipeline.py`의 파일명 회귀 테스트와 전체 테스트 묶음을 반드시 실행한다.
